# 2026-10-28

## 新活动击穿防误点机制（v1.2.18 现状分析，方案待用户拍板）

### 用户描述
游戏更新了新活动，入口位置正好压在盲点坐标上，而且该活动**本身也会进入战斗**，于是现有防误点机制全部失效。

### 现状四层防护（都是正向白名单）
1. `CombatFighter.run` 每轮：`_team_page_hit`(master_title+卡位勾) / `_home_page_hit`(main_arena_btn 全屏 0.85) / `_rank_up_hit`(rank_up_title ROI) → 命中即 break。
2. 每 4s `_escape_misnav`：`_detect_wrong` 只有 4 个模板（`wrong/wrong_user` / `wrong_rank` / `wrong_zhizun` / `wrong_shop`）+ `_main_page_hit`(arena_title/master_title) → 都不中 **return False = 恢复盲点**。
3. 每 4s 结算：`result_nodes=["Fight_Lose"]`，**胜利结算故意不查**（靠盲点自己点掉）。
4. 每 4s `_unknown_escape`：32x18 签名连续 5 次（20s）`absdiff < 1.5` 才点右上返回 —— **只对静态页（装备页）有效**。

### 失效链条
结算后残留盲点 → 打到主城的活动入口 → 活动页无模板 → `_escape_misnav` 返回 False → 继续盲点 → 点进活动战斗 → 活动战斗是动态画面，静止兜底永不触发、结算文字不匹配 → 打满 `duration=900s` → `Fight_Once.next` 7 个节点全不中 → 再耗到 `timeout=960000`（16min）→ Task failed，外壳仍打「任务已全部完成」。

**核心问题**：误点目标从「静止子页面」升级成「另一个战斗」，它同时否掉所有"已离开战斗"的判据、却满足"继续战斗"的判据。以前靠点返回能救回，现在是最坏情况（空转 + 可能消耗活动次数）。

### 提出的方案（三档）
- P0-1 **闸门单调性**：允许「战斗→离开」，禁止「离开→战斗」。`_escape_misnav` 的未知分支不再 return False，改为 UNKNOWN 只读观察（前 2 轮暂停盲点不退出，防大招/转场误判；连续 4 轮 ≈16s 仍未知 → 存图 + 停手）。
- P0-2 **认出结算即停手**：`_settle_visible`（win/lose/settle_confirm，本地 cv2）进主循环，命中立刻 break，把点「确认」交给 `Arena_SettleOk`，掐死「结算后残留盲点乱点」这条根。
- P0-3 `ArenaSafeBack` 加自限：连续 2 次点了画面无变化 → return False 让节点失败，避免 its next 里含自己的无限自循环。
- P1-1 **准入闸**：竞技场战斗 HUD 指纹（2~3 个 25x25 小块），未通过直接跳过盲点进三态判定。需要活动战斗截图来确认与竞技场战斗的差异点。
- P1-2 活动页加入 `_WRONG_DEFS` 黑名单（KNOWN → 点返回）。需要活动入口/活动页截图做模板。
- P2 Android 返回键（`controller.post_press_key(4)`，API 已确认存在）替代写死的右上 (1244,28)；`_find_red_back` 只找 x>=900，活动页返回键在左上，找不到就回退到错误坐标。
- P2 失败可见化：现在节点失败外壳仍报「任务已全部完成」。

## 就绪判据鲁棒性分析（用户问：CD 只变灰没数字能不能识别）

用户问：有的角色技能未就绪时只变灰、没有白色秒数，现有判据（ratio: V≥160 像素占比）还准吗？

**结论：那种情况恰好是安全的，但判据本身不是测"就绪"，是测"亮不亮"。**

- 「变灰无数字」→ 灰的 V≈90~140 < 160 → 占比≈0 → 判冷却。安全且比有数字更稳。
  模拟（把白字抹成暗部中位色 / 整体去饱和+压暗×0.55）：23 个冷却样本全部判冷却。
- 真正的弱点在**反向**：「有数字的冷却」白字 V=255，而 ROI 只有 27~35px 见方，
  一个秒数几乎填满 → 亮占比能到 **0.98**（s2 阈值才 0.35）→ 误判成就绪 → 白点一次。
  实测 s3 f045=0.937 / sec f051=0.656 / ult f048=0.976 都在阈值之上。
- 另一个方向（就绪偏暗）会漏判 → 靠 `ready_miss_rounds=4` 兜底。

**发现更好的判据：只测按钮外环。** 现状 ROI 正好压在中央秒数上；按钮的"就绪/冷却"

## v1.2.23：KO 判据按秒计时（commit 28fb765，未发版）

用户报「只剩最后一点点血的时候还是会停住」。**这次不用猜——v1.2.22 安装目录里就有实机日志**（`D:/Games/MaaKOF_Fate-win-x86_64-v1.2.22/logs/log-20261028.log`，含 agent print）。统计 14 次「敌方血量见底」：

根因：`enemy_gone >= 3` 是**连续 3 轮**，而 v1.2.20 起一轮 150~250ms → 3 轮只剩 **0.45~0.75s**，大招/连招特效盖住血条半秒就判 KO。**跟 v1.2.21 修 `ready_miss_rounds` 是一模一样的坑，当时只改了 ready 那一个阈值，KO 这个漏了。**（v1.2.20 时一轮 600ms = 1.8s 还够用。）

修法（三条）：
1. 血条连续消失满 `ko_gone_s = 2.0s`（真 KO 实测 6.2~14.6s，余量 3 倍以上）
2. 本回合此前见过 `≤ko_low_px = 12px`（真 KO 末帧实测 4px/8px；误判那三次遮挡时还有 33~85px，直接排除）
3. 兜底：没赶上「见过空血」那一帧（一次打掉 20px+，从 30px 直接跳没）→ 消失满 `2×ko_gone_s = 4s` 也算 KO（特效遮挡实测最长 1.7s，撑不到 4s）

实现：判定抽成 `CombatFighter._ko_step(hp_enemy, now, low, t0, min_px, ko_low_px, ko_gone_s) -> (low, t0, min_px, fire)`，纯函数式，测试直接调真身。**教训：测试里复制判据逻辑（v1.2.22 的 `ko_state_machine`）迟早漂移，能抽就抽出来。**

验证：`debug/_test_v1223.py` 24 项（实机三次误判时间线 + 两次真 KO + 边界 + 兜底 + 参数同步 + 源码无旧判据）；`_test_v1222` 20 项 / `_test_combat_v1220` 79 项 / `_test_combat_loop` 6 项（mock 时间线按真实 KO 时长重写，原来 KO 段只有 1.1s）/ anticlick / local_reco / rankup / nav_chain / pipeline_refs 全过。schema 校验通过。覆盖包 `MaaKOF_Fate_update_v1.2.23.zip`（70.2KB）。
