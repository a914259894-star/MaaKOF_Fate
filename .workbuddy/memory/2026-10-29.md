## v1.2.24 技能就绪判据统一换 bc（未发版，仅覆盖包）

用户报「技能识别阈值太高，有的角色的有的技能根本不点」，附截图（1140x649）：
一技能（最下面、粉紫、图标是女角色头像）亮着但从不点。

**定位过程（可复用）**：
1. `BUTTONS` 里 `normal=(1137,632)`（右下大圆，走盲点不做识别）、`skill1=(981,643)`。用 HoughCircles 在截图上找圆，按 x 反解缩放系数 K≈1.1135（6 个按钮一致性 1.1124~1.1147）→ 确认粉圆=skill1、大圆=普攻。
2. 实测该按钮 `ratio`（V≥160 占比）=0.29 < 阈值 0.45 → 每轮判冷却。**根因不是阈值数字高，而是 ratio 只看亮度**：亮紫 V 集中在 140~160 够不到 160，中心还是深色头像。
3. 同帧 bc（V≥150 且 S≥70）：就绪的 skill1 0.32、secret 0.55、substitute 0.56；带白字 6/8/1 的三颗全 **0.00** → 分离度极大。
4. v9 录像 195 战斗帧交叉验证：bc≥0.15 与旧判据仅 8 帧不同，**全部 ratio=1.00/bc<0.05 的白字帧**（旧判据在白点），没有一帧真就绪被漏。s2 那 4 帧 ratio=1.00 bc=0.00 是白字填满 ROI 的典型。

**改动**：`Fight_Skill1/2/3/Ult` 全部 `mode=bc / v_thresh=150 / s_thresh=70 / threshold=0.15`；skill3 的 `median-S 95` 废弃。`Fight_Secret` 保持 0.30（图标全角色共用）。ROI 一个没动。

**关键认识**：`ready_miss_s=10` 兜底判的是「连续 10s 一个技能都没就绪」，只要别的技能就绪就清零 → **单个技能漏放永远不会触发兜底**，会静默持续整局。

**测试**：`debug/_test_v1224.py` 39 项（含真实 1920 帧走 `_ready_hit` 复算、与 csv 差 ≤0.01；样本帧 `debug/skill_ready/newrole_ready.jpg`）。既有 9 个脚本全过，schema 通过。

**踩坑**：用 Edit 往 `interface.json` 的 welcome 字符串里插多行文本 → 真实换行未转义，JSON 直接解析失败（`Invalid control character`）。修法：取区间 `t[i:j].replace('\n', '\\n')` 再写回。以后改 welcome 一律用这个方式。


## v1.2.25 大师竞技选人后干等 36s（未发版，仅覆盖包，commit ae6f98e）

用户报「大师竞技第一个角色开战时要卡好一会」，附 `D:/Games/MaaKOF_Fate-win-x86_64-v1.2.22/logs/log-20261029.log`。

**量出来的事实**（agent 日志 + `debug/maa.log` 节点级记录双重印证）：
- 选人完成（`[OK] 禁用与选用均完成`）→ `CombatFighter 开始`：37.9 / 49.2 / 37.8 / 35.9 秒，**每局都这样，不是偶发**。
- 这 36~49 秒里 agent 侧一行日志都没有 → 全部花在 pipeline 的 `Arena_WaitBattle`。
- `Arena_MasterPick.next` 有 5 个节点（WaitBattle / MasterPage / Mode_Master / Enter_Master / MainPage），串行识别一轮 **2.0 秒**（Enter_Master 用了 3 张全屏模板 = 932ms，最贵），`rate_limit=1000` 之后再来一轮。
- 36 秒里 `Arena_WaitBattle` 的**候选框恒为 2 个**、分数 0.147~0.298 → ROI 里几乎没纹理 = 游戏在黑屏/纯色加载，**这段机器人真的没事可做**。

**真正能救的那 5~7 秒**：血条出现时候选框 2 → 34+（71px 等距横排 = 血条纹理），但最高分只有 **0.724~0.788**，差一点没到阈值 0.8，又空等：
- 12:54:17.408 0.788 → 12:54:22.972 0.948 命中，白等 **5.6s**
- 12:58:47.483 0.740 → 12:58:54.801 0.951，白等 **7.3s**
- 13:06:41.832 0.740 → 13:06:48.130 0.953，白等 **6.3s**
原因：血条刚出现的一两秒有开场发光/特效压着，分数上不去（稳定后 0.859~0.953）。

**阈值定 0.65 的依据**：把 maa.log 全部 120 条记录分档 → [0,0.3) 102 条、**[0.3,0.7) 0 条**、[0.7,0.8) 13 条、[0.8,1] 5 条。空档极大，0.65 落在中间，两侧余量 0.352 / 0.074。

**改动**：`arena.json Arena_WaitBattle.threshold` / `combat.json battle_threshold` / `combat_actions._battle_hit` 默认值 / `arena_actions._confirmed_away` 的 battle_hp1/2，四处一律 0.8 → 0.65。ROI 不动。

**方法论收获（复用）**：判断「识别慢/卡住」，先看 TemplateMatcher 日志里的 **候选框个数**——只有 2 个说明屏幕没纹理（加载页），30+ 说明目标已在画面里、问题在阈值。这条比看分数更快定位。另外 `logging: false` 时没有 maa.log，排查前先看 `config/maa_option.json`；本次用户环境是 `true`，直接就有节点级证据。

**未做**：等待期每轮 2 秒（5 个兜底节点串行）可以给那 4 个节点加 ROI 降到 0.5 秒，能再省 1~1.5 秒 + 降 CPU，但要动容错链，等用户确认是否值得。
